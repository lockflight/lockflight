# Commands

Every `lockflight` command, its options and its exit codes: a reference for the person running Lockflight and for anyone
reading what the agent ran.

**On this page:** [Running the engine](#running-the-engine) · [Setup](#setup) · [Gates](#gates) ·
[Lifecycle](#lifecycle-standard-profile) · [Human decisions](#human-decisions) · [CI](#ci) · [Exit codes](#exit-codes)

## Running the engine

In a project that is set up, run every command as `.lockflight/bin/lockflight <command>` from the project root (the directory
holding `lockflight.yaml`). That is the engine the hooks run: `init`, `link` and `update` keep it at the pinned version, it works
whatever way Lockflight was installed, and it needs no package feed (on Windows, Git Bash finds `lockflight.exe` by this name).
The skills tell the agent to run it the same way. Before a project is linked, use `~/.lockflight/bin/lockflight` (installed from
source) or `dotnet lockflight` (the tool pin, also what CI and teammates who restore the pin use). `lockflight --help` prints
the same list.

Commands that take `--feature <id>` resolve the feature in this order:

1. the explicit `--feature`;
2. Spec Kit's `SPECIFY_FEATURE_DIRECTORY` variable (a directory that does not exist is an error);
3. Spec Kit's `.specify/feature.json` (a malformed file, or one naming a directory that does not exist, is an error, not a
   fallback);
4. Spec Kit's `SPECIFY_FEATURE` variable, then the git branch, each read as Spec Kit's git extension names feature branches:
   the last path segment (`006-weak-spots` in `feat/006-weak-spots`) is the directory under `specs/`, else its number (`006`, or
   a `YYYYMMDD-HHMMSS` timestamp) picks the one directory with that prefix. A number that several directories share is an
   error; `SPECIFY_FEATURE` naming no directory is an error; a branch naming none (`main`) falls through;
5. the only feature, when there is exactly one.

This resolution does **not** apply to `approve verify`: it verifies exactly the feature named with `--feature`, or every feature
the change since `--base` touches, never a guessed one.

Each command accepts only its own options. An unknown option (`gate run --profil pr`), a stray argument, a repeated option or an
option without its value is a usage error (exit 4); a value starting with `-` (for example `--base -x`) counts as missing.

Everything the engine prints, on standard output and standard error and in hook messages, is made safe for a terminal: file
names, test names, spec text, ledger fields and branch names come from the project, so a control character or escape sequence in
them is printed visibly (`^[` for ESC, `<U+202E>` for a bidirectional override) instead of acting on your terminal. Line feeds
and tabs stay; the status line and Levi keep their own colours.

## Setup

| Command | What it does |
|---|---|
| `init [--profile lite\|standard] [--ci pr\|manual\|none] [--ci-platform github\|azure\|bitbucket\|gitlab] [--quality] [--architecture-tests] [--no-link] [--no-sandbox]` | Onboards the repository: `lockflight.yaml`, tool pin (in the existing `dotnet-tools.json`, else `.config/dotnet-tools.json`, else a new root one), `.gitignore`, `.claude/settings.json` (the plugin, an `Edit` deny rule per protected path: see [permission deny rules](guardrails-and-boundaries.md#permission-deny-rules), and the protected paths as sandbox write denials unless `--no-sandbox`: see [the Claude Code sandbox](guardrails-and-boundaries.md#the-claude-code-sandbox)), the CI workflow (installing every .NET channel the test projects target) and, for standard, `.gitattributes`. `--ci` sets when the workflow runs: `pr` on every pull request and push to `main`, `manual` only when started by hand (`workflow_dispatch`), `none` writes no workflow. Without `--ci` it is `pr`, except when the engine is a development build, which no package feed has: then it is `manual` and `init` says why (see [CI with a development build](getting-started.md#ci-with-a-development-build)). `--ci-platform` picks the CI service (default `github`): `azure` writes `.azure-pipelines/lockflight-gates.yml`, `bitbucket` writes `bitbucket-pipelines.yml` (or, when that file exists, `.lockflight/ci/bitbucket-pipelines.yml` to merge by hand), `gitlab` writes `.gitlab/ci/lockflight-gates.yml` and a `.gitlab-ci.yml` that includes it (an existing one is left alone and `init` prints the `include` to add); these templates are not yet verified on the live services, see [CI on other platforms](ci-other-platforms.md). `--quality` adds the recommended code-quality setup: `AnalysisLevel` `latest-recommended` in `Directory.Build.props`, the code metrics rules CA1502, CA1505 and CA1506 as warnings in `.editorconfig`, and their thresholds in `CodeMetricsConfig.txt`; a missing file is written, an existing one is never changed but gets a proposal patch (as `propose` writes) for a person to apply. `--architecture-tests` writes a layer dependency test project (ArchUnitNET) for the `.Domain`, `.Application`, `.Infrastructure` and `.Api` projects it finds, and refuses with fewer than two. Neither is on by default; see [code quality](code-quality.md), including the `baseline build` to record before the new warnings block. Then it links the engine. Idempotent; it only merges into existing files. It refuses, also before writing anything, when `.claude/settings.json` is not strict JSON (Lockflight reads and merges it as JSON without comments or trailing commas) or has an `enabledPlugins`, `extraKnownMarketplaces`, `permissions`, `sandbox` or `sandbox.filesystem` that is not an object, a `permissions.deny` that is not a list of rules, a `denyWrite` or `allowWrite` that is not a list of paths, or a plugin entry that is not `true` or `false`, rather than overwrite your settings. It never lowers a pin: when the tool manifest pins a newer engine, or a value that is not a version, or cannot be read, `init` refuses before it writes anything and says what to do (the `lockflight.cli` entry is found in any letter case). At a workspace shell root, a new manifest lists the child directories that look like units (their own repository, a solution, a `package.json`), and the child repositories are added to `.gitignore`. A root that builds by itself (a solution or project file at the root) is one repository: only child directories that are their own repository become units. |
| `doctor` | Readiness report: manifest, tool pin, whether the pinned engine can be restored (a development build from `scripts/dev-install.sh` is on no package feed: doctor looks for it in the local feed `~/.lockflight/feed` and the NuGet tools cache, without the network), a project still pinned to a development build once a release at or above it is installed (**development pin**: `update` moves it to the release), linked engine (a FAIL, without running it, when it was replaced since linking or has no hash record), whether the installed plugin works with the pinned engine (**plugin engine**: the plugin's `min-engine-version`, from the plugin this Claude Code session loaded, `--plugin-dir` included, when doctor runs inside the session, else the plugin at `CLAUDE_PLUGIN_ROOT`, else the install in Claude Code's record of installed plugins; the result names the copy it checked), `.gitignore`, Claude settings, the `Edit` deny rules (**deny rules**: one for every protected path `init` would deny now), the sandbox write denials (whether they cover the protected files that exist, and whether the sandbox is on), the Claude Code version (`claude --version`: a warning when it is older than 2.1.295, whose hooks do not block a tool call when the guard times out, or when it cannot be read), gitleaks (a warning without it: the `pr` profile's secrets step is NOT-EARNED, not PASS), Git Bash (Windows); in a project on the standard lifecycle (`init --profile standard` wrote its `.gitattributes` rule, or the Lockflight Spec Kit preset is installed and enabled, as `adopt apply` leaves it) PyYAML for Spec Kit, the Lockflight Spec Kit preset (a FAIL when missing) and the `claude` CLI; and — when `gates.coverage.collector` is set — the collector package in every test project. In a workspace it also checks:
<ul>
<li>that every unit is cloned;</li>
<li>that no unit has its own <code>lockflight.yaml</code>;</li>
<li>that child repositories are ignored by the shell;</li>
<li>that the plugin is enabled at user scope.</li>
</ul>
Any project gets a warning about a <code>global.json</code> that pins an SDK older than 10. In a git repository, two advisory lines summarise <code>docs check</code>: <b>docs drift</b> (references that no longer resolve) and <b>instructions size</b> (a <code>CLAUDE.md</code> or <code>SKILL.md</code> over Claude Code's size target); they warn at most. Each problem comes with its fix. |
| `doctor --self-test` | A quick self-test of this engine build on this machine, instead of the readiness report. It plants five violations in a temporary scratch project (never your project) and prints each as `caught`, `MISSED` or `BROKEN` (its harmless twin was refused too, so the result proves nothing): the guard on an Edit of `lockflight.yaml`, `approve spec` under `CLAUDECODE=1`, `doctor`'s check on a linked engine without a hash record, the test gate on a failing test (both test platforms), and red on `Assert.Fail`. Under a second, no build, no network; it works outside a project. Exits 1 when any canary is not caught. The full canary suite, a violation in front of every guard rule, gate step and human-only command, is part of the engine's tests and runs in CI on Linux, Windows and macOS. `--canaries` and `--canaries=full` are deprecated names for `--self-test`: they print a note and run it. See [every safeguard red at least once](guardrails-and-boundaries.md#every-safeguard-red-at-least-once). |
| `docs check` | Lists the references in your instructions and docs that no longer resolve, and instruction files over Claude Code's size targets. It reads, at and below the project root (the directory holding `lockflight.yaml`, else the current directory), the tracked `CLAUDE.md` files (any depth), `.claude/rules/`, the Spec Kit constitution, skills (`skills/<name>/`, plugin skills included), `docs/` and the root `README.md`; it leaves out changelogs, `decisions/` and `adr/` folders, `specs/` and the `speckit-*` skills Spec Kit installs, because those record history. It reports: a Markdown link or image to a file that does not exist; a link to a heading the target file does not have (GitHub's heading anchors); a path in a code span that git history deleted or renamed (it names the commit and the new path), or whose file is in another directory of the same tree; an engine command line (`lockflight …`, `.lockflight/bin/lockflight …`, `dotnet lockflight …`, in code spans and shell code blocks) with an unknown command or an option the command does not take; a `/plugin:command` of a plugin the repository holds that has no such skill or command; a `CLAUDE.md` over 200 lines or a `SKILL.md` over 500 (Claude Code's own targets), with its longest sections and where each could go. A path the repository never had is not reported: most such paths in instructions are another project's files, run-time files or examples. In a shallow clone history is partial, and the output says so. A line with `<!-- lockflight: drift-ignore -->` is skipped, for a deliberately wrong example. Read only, no network, no build. Exits 1 when it finds something and 4 outside a git repository. No gate runs it: to see it in CI, add a step that runs it (with `fetch-depth: 0` on checkout, for the history) and mark the step `continue-on-error` if it must not fail the job. |
| `rules audit` | Lists every rule in your instruction files, the tracked `CLAUDE.md` files, `.claude/rules/`, the Spec Kit constitution and skills (not the `speckit-*` skills Spec Kit installs), with what backs it. A rule is a sentence of a list item or table cell with `MUST`, `NEVER`, `ALWAYS`, `SHALL`, `DO NOT` or `REQUIRED`, or with `never`, `always`, `must`, `do not` or `don't`; in a paragraph, a sentence with an upper-case marker or that starts with a lower-case one. Each rule is **checked (G)** when a Lockflight guardrail refuses exactly what it forbids: it bans editing, writing or deleting a path in a code span that the protected list covers (the guard), or it bans running a human-only command (the engine refuses it inside Claude Code). It is **related** when a check touches it without proving it: a symbol that a `BannedSymbols.txt` lists, with what is missing (RS0030 is a warning, so the build gate fails it only as a new warning against an existing baseline; only projects that add the file as `AdditionalFiles` are analysed; a suppression is not blocked); an analyzer id (`CA1502`) or the metric a code metrics rule measures ("cyclomatic complexity") that a tracked `.editorconfig` or `.globalconfig` sets to `warning` or `error`; or a dependency ban between two named layers when a test uses ArchUnitNET or NetArchTest ([code quality](code-quality.md#rules-audit)). Everything else is **guidance only**, sometimes with a suggestion it never applies: a `protected:` entry for a path the rule says not to edit, a `BannedSymbols.txt` entry for an API it bans (the id is not verified), a `dotnet_diagnostic` severity line for an analyzer id, or `init --architecture-tests` for a dependency ban. The mapping uses exact matches from your configuration, never a model, and never says "enforced": none of these is a boundary ([guardrails and boundaries](guardrails-and-boundaries.md)). Grouped per file; read only; exit 0, or 4 outside a git repository. |
| `statusline` | Claude Code's status line command: reads the session JSON on stdin and, in a Lockflight project, prints Levi's face and the last verdict from the local ledger (a guard block, a red Stop gate, a gate run or a review run in the past day), or `on duty` when there is none. While a code from an in-session human command waits for its second step, it shows the line to type instead, for example `approval waiting: type /lockflight:approve spec <code>`. A usage hint or a wrong or expired code is not a block: it is ledgered as `session-command.answered`, which neither the status line nor `ledger retro` counts. Plain text under `NO_COLOR`; nothing outside a Lockflight project. See [Levi and the status line](getting-started.md#levi-and-the-status-line). |
| `adopt plan` | Reads an existing Claude Code and Spec Kit setup and writes `.lockflight/adopt/plan.md`. It covers the hooks (the project's, each unit's and your user-level ones, read only), skills, agents, commands, Spec Kit, existing features, `CLAUDE.md` and directories that look like units, and gives each one an action: keep, protect, flag, add, upgrade or mark. The plan, and the command's output, end with the `adopt apply` line to paste into a separate terminal window: `cd` to the project root, the linked engine, and — when Spec Kit is upgraded — `--speckit-preset` with the absolute path of the preset found on this machine (the installed plugin's, else the source checkout's), or a placeholder when none is found; `--skip-speckit` leaves Spec Kit as it is. Nothing is changed. |
| `workspace sync [--check]` | In a workspace shell, writes into every .NET unit that is its own repository the files its CI needs: `lockflight.unit.yaml` (the shell's policy re-based to the unit), the engine pin, the unit's baselines and the CI workflow. The workflow is generated policy too: a missing one is written, and an edited one (a `continue-on-error`, a skipped step) is rewritten to the generated one, and the output says so. `--check` changes nothing and exits 1 when a unit is behind the shell, an edited workflow included. See [CI hardening](ci-hardening.md#workspace-shells-unit-repositories). |
| `link` | Copies the pinned engine to `.lockflight/bin/`, where the hook shim runs it in about 5 ms instead of `dotnet tool run`, and records its SHA-256 beside it (`lockflight.sha256`): the shim does not run an engine replaced afterwards, nor one without a record (linked before 0.2.0-alpha.7 or copied in by hand; `update` links it again and writes the record). |
| `version` | Prints the engine version. |

## Gates

| Command | What it does |
|---|---|
| `gate run [--profile edit\|stop\|pr] [--path <dir>] [--unit <path>[,…]] [--base <ref>] [--result <file>]` | Runs a profile (default `stop`) on the repository or `--path`; a `--path` inside a unit uses that unit's `build:`, test framework and stop filter. A `stop` run over the stop target (no `--unit` or `--base`) caches its PASS like the Stop gate, so a task can then be marked completed and the next Stop gate answers from the cache. At the root of a workspace with units, it covers every unit changed since its last PASS, committed or not (`pr`: every unit), or the `--unit` ones; a unit that is not cloned in this checkout is reported as `not present in this checkout` (N/A). `--base` sets the comparison point for format, suppressions, coverage, secrets and protected changes (the branch's changes since the merge base count as changed). `--result` writes the JSON result envelope. The stop profile's budget is capped at 540 s, below the plugin's Stop hook timeout. |
| `hook <event>` | Called by the plugin. Reads Claude Code's hook JSON on stdin and answers with an exit code or JSON. The plugin registers `session-start`, `pre-tool-use`, `user-prompt-expansion`, `task-completed` and `stop`. The engine also accepts `post-tool-use` and `subagent-stop` (logged only); an event it does not know is blocked with a message to update the engine. |

Profiles and steps are described in the [configuration reference](configuration.md#gate-profiles).

## Lifecycle (standard profile)

| Command | What it does |
|---|---|
| `phase check specify\|tasks [--feature <id>]` | Phase-exit checks on the [spec contract](spec-contract.md). **specify:** requirement IDs, uniqueness, clarifications, no Spec Kit template placeholders left, stories. **tasks:** spec approved, every requirement covered, every story task cites one (an `FR-xxx` anywhere on the line), tests first. A task is a test task under a `### Tests for …` heading, when it starts with test wording ("Write tests …", "Spec for …", "Cover … with tests"; not "Make tests pass …" or "Run tests …", which write no test) or when it names a test file (`*.spec.ts`, `*.test.tsx`, `*Tests.cs`, a `*.Tests/` project) and does not start with "Implement" or "Make". A stub task ("stub", "skeleton", "declare/scaffold signatures", `NotImplementedException`) may sit anywhere. A failure names each misplaced task, its line and why it counted as implementation. |
| `redgreen start [--feature <id>]` | Records the write-once baseline of existing tests. It needs a valid tasks approval. It runs the whole suite once (on a large suite this takes minutes) and warns about tests that already fail (a person accepts them with `baseline tests`, merged in its own pull request first). |
| `redgreen red [--feature <id>] [--verbose]` | Refused while the spec or tasks approval is stale (as is `green`). Builds, finds the new tests, runs them and classifies each failure. Under each test a line says why it got its class: where it failed, and the production member the test reaches or that it reaches none (naming a production type, as a type argument of `Deserialize<T>` or in `typeof`, is not reaching it; a call, a constructor or a property read is). `--verbose` adds the exception type, the deciding stack frame with its file and line, and the production call found. A cycle is accepted only when every new test fails because of production code: RED_STUB (a `NotImplementedException` from production code) or RED_ASSERT (an assertion in a test that calls production code: xUnit's, or Shouldly, FluentAssertions, AwesomeAssertions, NSubstitute, Moq or Verify, listed in the [glossary](glossary.md)). Production code is every project that is not a test project and does not reference xUnit; "calls" is read from the built test assembly (the test method and the helpers, lambdas and async bodies of the test project it reaches). That shows the test exercises production code, not that the failing assertion compares its result: the review judges that. Rejected tests are listed with what to change (RED_IN_TEST, RED_OTHER, RED_NO_PRODUCTION, GREEN_BEFORE, SKIPPED, FLAKY). A new test whose code (with the test project's helpers it reaches) neither calls an assertion library or an assertion-named method (`Assert…`, `Verify…`, `Should…`, `Received…`) nor throws is marked **assertion-free**: a warning on its line and in the trace, not a rejection, because a test may verify by letting the production code throw, which reading the test code cannot tell apart. It is refused when a known test was skipped or marked `Explicit` since the baseline. New tests that pass are re-run to tell FLAKY from GREEN_BEFORE: at most four batched re-runs, all inside the red's `gates.timeoutSeconds` budget. If the budget runs out, the remaining tests stay GREEN_BEFORE and the red is still rejected, because a test that passes before the code exists rejects the red either way. An accepted red keeps a **red-time snapshot**: the working tree as it was when the red started (tracked, staged and untracked files that are not ignored, without `bin/` and `obj/`) as a git commit object under `refs/lockflight/red/<feature>/<cycle>/<commit>`, written through a private copy of the index, so your index, branch and stash are untouched. The ref is local only; Lockflight never pushes it (see the [glossary](glossary.md)). The output names any untracked file in it that does not look like source. No snapshot is taken outside git or when a test project is in another repository of a workspace. |
| `redgreen green [--feature <id>]` | The cycle's tests pass (they run first; if any still fails, green stops without running the suite), nothing else broke, and no tests were deleted, newly skipped or newly marked `Explicit`. Explicit tests are read from the runner's listing, because a normal run reports them as not run. The full run must also be complete: a runner that crashed or timed out, or a report missing known tests, rejects the green. Before building, green compares every file of the locked test projects with its hash at red (or after an amend's red): a file changed, added or deleted since, without a recorded amend, is refused with its name and how to amend it. The hashes are taken when the red starts, and a red whose test files changed while it ran is refused. Not compared, because builds, test runs and editors write them: `bin/`, `obj/`, non-C# files in `TestResults/` and snapshot-test `.received.` files, dot-files, and `*.user` or `*.swp` files. Line endings do not count (CRLF reads as LF), so a checkout that converts them is not a change. A test project at the repository root is not compared, because it would cover the production code. Cycles recorded by an older engine have no hashes and are not compared. |
| `redgreen status [--feature <id>]` | Shows the cycles and whether tests are locked. |
| `trace [--feature <id>]` | A Markdown matrix of each requirement and the tests that went red, then green, for it. It builds and lists the current tests (it runs none). A test counts only while it still exists, still names the requirement, and is neither skipped nor explicit. A requirement whose last such test is gone fails the trace. An assertion-free test still counts, marked `(assertion-free)`, with a note to check it in review. If the build fails, or the spec defines no requirements, the trace is NOT-EARNED. A stale spec or tasks approval prints a warning line. |
| `review [--feature <id>] [--base <ref>] [--model <name>] [--budget <usd>]` | Runs the reviewer on the diff against the base (default: the target branch, `review.target`, else the branch `origin/HEAD` points at, else `main`) with the manifest's `review.model` and `review.maxUsd`, else `sonnet` and `3.00`. The prompt's instructions are the engine's own; the spec, the diff, the base commit's `CLAUDE.md` (the working tree's is not read, so the change cannot rewrite its reviewer's guidance) and the reproduction context below go into fences marked as data. Blocker and major findings need a reproduction `[Fact]`; the engine runs it (the method with a test attribute: `[Fact]`, `[Theory]`, `[Test]`, `[TestCase]` or `[TestMethod]`, so a helper written before it is not taken for the test; without one, the first `void` or `Task` method): a failing one confirms the finding, a passing one rejects it, and a missing or broken one (or tests that do not build) leaves it unverified. To help it compile, the prompt lists the test projects (frameworks, references, the using directives the engine adds), the signatures of the changed C# files and a sample test. Each reproduction is built in the test project nearest the cited file (the one that contains it or references its project), from a temporary file and into `bin/lockflight-review/` and `obj/lockflight-review/` (a review that starts while another one of the same project is building uses a folder of its own and removes it afterwards), so your sources and your own build output are not touched. A new finding's reproduction that does not compile goes back to the reviewer once with the compiler errors and the cited file's signatures, within the run's budget: a repaired reproduction that fails confirms the finding, one that passes leaves it unverified (`repaired-passed`). The prompt tells the reviewer that a reproduction's assertion must encode a requirement sentence of the spec, or behaviour an existing test defines, and that a finding the spec is silent on is minor; that is guidance to a model, not a check. A finding may quote the requirement sentence it encodes (`specQuote`; for a minor or nit finding too): the engine records it as `anchored` when, with runs of whitespace made one space and Markdown emphasis and code markers removed from both (`**`, `__`, `*` or `_` at the edge of a word, and backticks, so `**Given** … **When** …` matches the same words without asterisks, while `retry_count` and `2 * 3` stay as written), it appears word for word in the spec (case counts; at least three words), as `not-anchored` otherwise, and `none` without a quote. The output, `review status` and the pull request summary show it next to the finding; it does not change a blocker/major finding's outcome or the exit code, so a person reads it. The prompt tells the reviewer that a finding violating a MUST or SHALL sentence is at least major, and that any finding with a `specQuote` carries a reproduction (and a fix) whatever its severity. **Escalation.** A minor or nit finding is raised to major by the engine only when all of these hold: its `specQuote` is `anchored`, the quote contains `MUST` or `SHALL` (upper case, as a whole word, as in RFC 2119), and its reproduction fails on the current code. Its reproduction runs with the blocker/major ones, in the same builds and within the same limits: one repair within the run's budget when it does not compile, each build and run within `gates.timeoutSeconds`. An escalated finding is confirmed, goes through the fix check, opens and can be dismissed like any other major finding; the run file keeps the reviewer's severity (`originalSeverity`) and says `escalation: "escalated: anchored MUST, reproduced"`. A candidate whose reproduction passes, does not compile, could not be repaired because the budget was spent, or did not run stays at the reviewer's severity, and `escalation` says which (`not escalated: …`); the severity is never changed silently. **Fix check.** A blocker/major finding may also carry a minimal `fix`, a unified diff of existing C# files outside the test projects. Before a new confirmed finding counts as a FAIL, the engine applies its fix to copies of those files (your files stay as they are), builds them with the reproduction into `bin/lockflight-review-fix/` and `obj/lockflight-review-fix/`, and runs the reproduction together with the change's own tests: the test methods in the test project the reproduction runs in whose lines the diff adds or changes. Hunks are placed by their lines, not by the line numbers in their headers. If the fix makes the reproduction pass but one of the change's own tests fails, the reviewer's expectation contradicts what the author's tests encode: the finding is **contested** (NOT-EARNED, not FAIL) and the output names the test. A fix that does not apply (it names a test file, adds, removes or renames a file, or its lines are not in the file) or does not build goes back to the reviewer once, within the run's budget, like a reproduction. If it still does not apply or build, the finding stays confirmed (FAIL) with `fixChecked: false` and `fixCheck: did-not-apply` or `did-not-build`: a broken diff says the reviewer got the diff wrong, not that the finding is. The exception: when every error of the fixed build is in one of the change's own test files (the fix changes what those tests use; matched by file name), the fix contradicts them, so the finding is contested (`breaks-own-test-build`) and the output names those files. A fix that holds leaves the finding confirmed and `fixChecked: true`. A finding without a fix, or whose fix leaves the reproduction failing (`did-not-fix`) or whose fixed build does not run, stays confirmed as before, with `fixChecked: false`. There is at most one fix check (and one repair) per new finding, each build and run within `gates.timeoutSeconds`; findings open from earlier runs are not checked again, and a contested one stays contested while it is open. The check is a guardrail on the reviewer's evidence, not a proof: the fix and the reproduction are both the reviewer's, the change's tests may be the ones that are wrong, and only tests in the reproduction's test project run. A person decides a contested finding (fix the code or the test, or `review dismiss` it). The run file records each check (`fix`, `fixCheck`, `fixChecked`, `conflictingTests`, `fixAttempts`) and the run's `fixChecks` count and wall time, which the output also prints. Each finding gets a stable id (from its file, line and claim). A confirmed or unverified blocker/major finding stays **open** across runs: every later review re-runs its reproduction, and every earlier reproduction of it that differs, and closes it as fixed only when all of them pass; otherwise only `review dismiss` closes it, so a later clean run does not make it disappear, and a later run that raises it again as minor or nit keeps it at its higher severity. Each run is stored in `.lockflight/features/<feature>/reviews/` with the base, its merge base, the model, the budget, the Claude Code version, tokens, the estimated cost (repairs of reproductions and fixes included), the wall time and every finding's outcome, reproduction attempts and compiler errors. The reviewer is shown at most `review.maxDiffCharacters` characters of the diff (default 120,000; from 10,000 up to the engine's ceiling of 400,000): when the diff is longer, it gets the files whose diffs fit whole and a list of the others to read, and the run says, before the reviewer starts, that it will not be of record. **Generated files** are listed, not shown: the package lock files (`packages.lock.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`), EF Core model snapshots (`Migrations/*ModelSnapshot.cs`) and migration designer files (`Migrations/<name>.Designer.cs`, only when the migration `<name>.cs` is in the diff or the tree; the migration itself is shown in full). The choice is by path only: an `// <auto-generated />` header or a `linguist-generated` attribute never hides a file, since the change under review could add them. A snapshot or designer file whose content does not look like EF Core's generated code (the `// <auto-generated />` header, then only usings, a namespace, the `[DbContext]` and `[Migration]` attributes, one partial class with its `BuildModel` or `BuildTargetModel` override, and model-builder calls with literal arguments) is shown in full, and so is a generated file that was deleted. The reviewer gets each listed file's path, size and SHA-256 and may read it; listed files do not count toward the limit, and the run file records them under `generatedFiles` as listed, not reviewed.  The diff is taken without external diff tools or text conversions (`--no-ext-diff --no-textconv`); a changed file that git shows as binary although its content is text (no NUL byte in its first 8,000 bytes, on either side), such as one a `.gitattributes` `-diff` line hides, is named after the diff for the reviewer to read, and the run says before the reviewer starts that it will not be of record; a real binary file stays a one-line entry, and a generated file is checked the same way. A run is the **review of record** only when the reviewer was shown the whole diff (generated files listed aside, none of it cut, no text file shown as binary) of a clean tree, with the manifest's model, budget and diff limit, against a base whose commit is the merge base of HEAD and the target (not an older base, and not a recent commit on the branch); any other run says why it is not. A clean tree means that nothing the review reads differs from HEAD: no changed or staged file and no untracked file in the diff's paths or the feature's `spec.md`. Files git ignores, `.lockflight/`, `.claude/worktrees/` and untracked `bin/` and `obj/` folders do not count, and nor do the other files under `specs/`, which the diff leaves out. Such a run still reviews the working tree and its findings count, but it says before the reviewer starts that it will not be of record and names the files (an untracked one is not in the diff at all): commit them, or stash them (`git stash -u` also stashes untracked files), and review again. For a change too large to review whole, split it into smaller pull requests and review each, or raise `review.maxDiffCharacters` (a larger diff costs more, so `review.maxUsd` may need raising too). Exit codes: 1 when an open finding is confirmed, 5 when one is unverified or contested or a clean run is not of record, 0 otherwise. While a red cycle is open, a review is refused (exit 1, before the reviewer runs) when a locked test file changed since its red without a recorded amend, as `redgreen green` refuses. |
| `review status [--feature <id>]` | Read only: the runs in the order they were recorded (and which are of record), the open, fixed and dismissed findings, and a summary for the pull request body with the base, the target, the merge base, the number of review runs and every open finding, each with whether its spec quote is anchored and, for a confirmed or contested one, what its fix check showed. The summary also lists every amended test with its diff since the red. A run file that cannot be read (not JSON, no time, no findings) is listed with the reason and counts for nothing; one without its base is read but not of record. |
| `ledger retro [--days 30] [--min 2]` | Recurring incidents from the local ledger, each with a suggested remedy. |
| `propose <path> (--from <file> \| --delete) [<path> …]` | Proposes a change the agent may not make itself, such as an edit to a protected file. `<path>` is a project file (existing or new, protected or not); `--from` names a file outside the protected paths (typically the agent's scratch directory) that holds its complete new content, and `--delete` proposes removing it. Several pairs may be given; each file gets its own git patch in `.lockflight/local/proposals/<yyyyMMdd-HHmmss>-<name>.patch` (git-ignored), with `a/` and `b/` paths relative to the project root and line endings kept. For each it prints whether the file is protected and by which rule, a **high risk** flag for build configuration (`*.props`, `*.targets`, project files), analyzer and code-style policy, Claude Code hooks and settings, CI workflows, NuGet configuration, `global.json` and Lockflight's own policy, a diffstat, and the command for you: `git apply --check <patch> && git apply <patch>`, run at the project root. It applies nothing. Symbolic links are resolved first, so the patch names the real file (and its rule), and on a case-insensitive file system the stored spelling. It refuses (exit 4, no patch written) a path outside the project or inside `.git`, a name with a control character, a `--from` file inside a protected path (also through a link), binary content, a file larger than 8 MB on either side, content identical to the file, and a proposals directory that is a symbolic link or a file. If one pair is refused, no patch is written for any. The ledger records `proposal.created` with the path and rule, never the content. The agent runs it; the guard still blocks the agent's own `git apply`. |

A red/green step whose tools cannot build-and-list, list or run the tests ends ERROR (exit 3): that says nothing about the
tests. A build that fails is a verdict (FAIL, or COMPILE_RED for a red).

After the build, red/green, `trace` and `review` find the test projects by evaluating every `.csproj` under the root (or the
unit) with `dotnet msbuild -getProperty`, all within `gates.timeoutSeconds` together. A project that evaluates and is not an
xUnit test project is left out. A project whose evaluation fails or times out might be a test project whose tests would be
left out, so `redgreen start`, `red` and `green` and `trace` end NOT-EARNED (exit 5), naming the project and the first line
of the error (or the timeout); an amend's re-check does the same, and the amend stays open. `review` still runs, but it runs no
reproduction, so its blocker and major findings stay unverified. Fix the project so `dotnet msbuild <project>
-getProperty:IsTestProject` succeeds, remove it if it is not meant to build, or, for a timeout, raise `gates.timeoutSeconds`.
No setting excludes a project from discovery. The `test` gate runs `dotnet test` and does not use this discovery.

## Human decisions

> [!IMPORTANT]
> These refuse to run inside a Claude Code session (exit 2), and that includes a `!` command typed in Claude Code. Run them
> in a separate terminal window.

A `!` command runs inside the session and is refused. The refusal says to open a separate terminal window first and then
gives the line to run there, inside the sentence, for example: Open a separate terminal window (not with `!` in Claude Code:
that runs inside the session and is refused) and run `cd '/path/to/project' && .lockflight/bin/lockflight approve spec`. Or
type /lockflight:approve spec in Claude Code. Every hand-off from the engine, the guard and the skills follows the same
order: the session command when there is one, else the separate terminal window, and only then the command line. A spec or tasks approval can also be given in the session
by typing `/lockflight:approve`, and a baseline, a reset or an amend by typing `/lockflight:baseline`, `/lockflight:reset` or
`/lockflight:amend` (below). `update` and `adopt` run in a terminal only.

Every in-session command works the same way. It counts only when **you type it** in an interactive session, not for the
agent's own skill call, a headless `claude -p` session or a scheduled turn. It takes two steps:

1. Type the command. The engine shows you, and not the agent, what would be recorded and a one-time code. Claude Code puts
   "UserPromptExpansion operation blocked by hook" above it; that is not an error. The message starts with
   `Step 1 of 2 — nothing has been … yet` and ends with the line to type, for example
   `Type within 10 minutes: /lockflight:approve spec 9u2bx9`.
2. Type that line within 10 minutes. The code works once, and only while what you were shown stays unchanged. The
   confirmation starts with `Step 2 of 2 —`.

Typing the command again shows a new code and the earlier one stops working. A fifth wrong code discards it. The command alone
(`/lockflight:approve` with no phase, `/lockflight:baseline` with no kind, `/lockflight:amend` with no test) while a code waits
tells you the line to type; the engine keeps only a hash of the code, so you take the code from the step 1 message. When the
engine is missing or fails, the command is refused, not passed on to the agent. Every refusal ends with the command for a
separate terminal. Waiting codes live in `.lockflight/local/session-approvals/`; one that is unreadable, written for another
command or replaced by a link records nothing.

| Command | What it does |
|---|---|
| `approve spec\|tasks [--feature <id>]` | Records an approval bound to the artifacts' hashes. It first runs the matching phase check (`phase check specify` for the spec, `phase check tasks` for the tasks, which also needs a valid spec approval) and, while any item fails, records nothing (exit 1) and lists the failures with how to fix them: add the missing Given/When/Then scenarios or rewrite the spec to `.specify/templates/spec-template.md`, correct `tasks.md`, then run the check again. The record is the local loop's guardrail; the approval of record is the platform's review of the pull request ([CI hardening](ci-hardening.md#approvals-of-record-the-platforms-review)). A `.sig` file a 0.2 engine wrote next to a record is ignored. |
| `/lockflight:approve spec\|tasks [--feature <id>]`, typed in Claude Code | The same approval without leaving the session, in the two steps above. Step 1 shows each file with the start of its hash, the requirements and stories (spec) or the task counts and covered requirements (tasks), open `[NEEDS CLARIFICATION]` markers and the current approval. Step 2 is `/lockflight:approve spec <code>`. `--feature` takes a feature ID (a directory name under `specs/`), not a path. Both steps run the same phase check as the command and refuse while it fails, so step 1 shows no code for a spec or tasks that would fail. Nothing is recorded when anything is off: a wrong, used or expired code (also after the clock went back), a changed file or unknown options. The record and the ledger line are the same as the command's (the ledger's `channel` says `session`). |
| `/lockflight:baseline build\|tests\|deps\|suppressions [--path <unit>]`, typed in Claude Code | `baseline` in two steps. Step 1 runs the full build, the tests, the advisory listing or the suppressions scan (at most 540 s, below the hook's 600 s limit) and shows every entry it would accept (up to 40 lines, then a count; the code binds all of them), how many are new compared with the current baseline, and the file it writes. Step 2, `/lockflight:baseline build <code>`, writes exactly those entries without running anything again, and only while no file in the repository changed since step 1 (tracked changes and untracked files that are not ignored; `.lockflight/` and `.claude/` are left out). It needs a git repository. `--path` takes a unit listed in `lockflight.yaml`. |
| `/lockflight:reset [--feature <id>]`, typed in Claude Code | `redgreen reset` in two steps. Step 1 shows the evidence that would be discarded: the baseline, each cycle and its state, every amend, and the red-time snapshot refs that go with it. Step 2, `/lockflight:reset <code>`, deletes the record and those refs while the record is byte for byte as shown. |
| `/lockflight:amend <Class.Method> [--feature <id>] --reason <why>`, typed in Claude Code | `redgreen amend` in two steps. The reason is the rest of the line, so it comes last. Step 1 shows the test, the file it unlocks, the other tests of the cycle in that file, the reason and who will be recorded. Step 2, `/lockflight:amend <Class.Method> <code>`, records the amend with the reason shown, while the record and the files declaring the test are unchanged. |
| `redgreen reset [--feature <id>]` | Discards the feature's red/green evidence (and says so when there is none), and deletes the refs that keep its cycles' red-time snapshots (`refs/lockflight/red/<feature>/…`); it names each ref it deleted. Refs that another worktree's record names are left alone. |
| `redgreen amend <test> --reason "<text>" [--feature <id>]` | Lets one test of the open red cycle change after its red was accepted, when its expectation is wrong or the API it uses changed. `<test>` is `Class.Method` (or the full name, or the method name when it is unique in the cycle). The file that declares the test becomes writable for the agent, and only that file: the output names it, and the other tests of the cycle in it, which the amend makes writable too. Commands that rewrite a whole directory stay blocked. The file stays writable until the next `redgreen red`, which re-checks only the amended tests: they must fail in production code again (RED_STUB or RED_ASSERT), with no test lost and none added; otherwise the amend stays open. The re-check runs on the cycle's red-time snapshot, in a temporary git worktree inside the repository's git directory (`.git/lockflight/`) with the current content of the cycle's amended files laid over it, so an implementation written since the red cannot make the amended test pass. The amended test must therefore compile against the code as it was at red; one that needs an API added after the red, or a file git ignores, is refused with the build errors. The worktree is removed afterwards. A cycle without a snapshot (recorded by an older engine, or outside git) is re-checked on the current tree, as the output says. The rest of the cycle's evidence is kept, and `green` is refused while an amend waits for its red. The red/green record keeps who (git `user.email`), when and why; the ledger gets `redgreen:amended`. The red that re-checks the amend records the diff of its files since the red-time snapshot: the diff itself (up to 200 lines), its SHA-256 and a summary such as `+1 -1 lines in tests/Shop.Tests/ShippingTests.cs`. | `review dismiss <finding-id> --reason "<text>" [--feature <id>]` | Closes an open review finding you judge not to be a defect. A dismissed finding stays closed when a later review raises it again. |
| `baseline build\|tests\|deps [--path <dir>]` | Accepts the current build warnings, failing tests or vulnerable-package advisories (brownfield adoption). In a workspace, `--path <unit>` writes that unit's own baseline. |
| `baseline suppressions` | Accepts the suppressions the branch adds since it left the default branch (`origin/HEAD`, else `main`), uncommitted ones included, by file and rule (`src/Order.cs\|CA1822`), adding them to those accepted before: the `quality.suppressions` step then lets that rule be suppressed in that file. <li>adds the guard hooks' paths to <code>protected:</code>, the units, and a Lockflight block in <code>CLAUDE.md</code>;</li>

</ul>

## Exit codes

| Code | Meaning |
|---|---|
| 0 | PASS; also a gate run whose steps were all N/A (for example `edit` with no changed C# lines) |
| 1 | FAIL |
| 2 | blocked: a hook decision, or a human-only command run by the agent |
| 3 | ERROR: the engine or a tool it ran broke (including a tool that is not on PATH). This is not a verdict about the code |
| 4 | configuration: invalid command line (unknown option, missing value), manifest or target |
| 5 | NOT-EARNED: nothing to judge, for example zero tests. Never a pass |
