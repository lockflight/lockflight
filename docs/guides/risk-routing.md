# Risk routing

How much evidence a pull request needs should not be up to the person who opens it, and never up to the agent that wrote it.
Risk routing reads the pull request's diff and computes its **change class**; the class decides which checks the pull request
must pass. For the person who owns a project's policy and for reviewers who want to know why a pull request is in its class.

> [!IMPORTANT]
> Risk routing is being built. This version computes the class and what it requires, and `lockflight route show` prints both;
> no check uses the class yet. Nothing on this page is in force until the release notes say so.

## The four classes

| Class | Meaning in one line |
|---|---|
| `fix` | a small change to existing production code: no new files, types or surface |
| `behaviour` | any other change to production behaviour that adds no API and touches no database schema |
| `feature` | a change that adds or changes an API (HTTP endpoints, a library's public surface) or the database |
| `critical` | touches a path the base branch's manifest marks critical, the policy, or the build and solution structure |

Three rules shape everything else:

- **Raising is allowed, lowering never.** Every input can only push the class up; nothing in the pull request pushes it down.
- **When unsure, classify higher.** An ambiguous case resolves upwards.
- **The class is a pure function of the diff and the base branch's policy.** No build, no network, no clock: the same commit
  pair and the same policy give the same class.

## Which diff is read

- **In CI:** the zero-context diff of `merge-base(base, head)..head`, where head is the pull request's head commit and base is
  the tip of the branch it targets. Never the platform's merge ref: its diff changes when the base moves on, and its head is
  a commit nobody wrote.
- **Locally:** one `git diff <merge-base>` against the working tree (committed and uncommitted changes in one, so a line is
  never counted twice) plus untracked files. In a workspace, every unit with its own repository is read the same way and its
  paths are reported under the unit path.
- **Renames are a delete plus an add**, so the old path of every move is in the diff too, and a deleted file keeps its
  removed lines.
- **git is pinned against your configuration:** Myers diff, no external diff drivers or text conversion, fixed prefixes,
  submodules compared. A `diff.algorithm` or a `textconv` filter in your settings cannot change the counts between a local
  run and CI.
- A base that names no commit (or the all-zero id of a push without one) is reported as "no base", and a failed git call (no
  merge base in a shallow clone, unrelated histories) as an error. Neither is ever read as "no changes".

## File roles

Each changed path gets one role, first match wins. Every name test ignores case (`.CSPROJ`, `directory.build.props`).

| Role | Rule | Counts toward size |
|---|---|---|
| `non-production` | matches `routing.generatedPaths` or `routing.nonProduction` on the base branch | no |
| `generated` | a package lock file, or `Migrations/*ModelSnapshot.cs` and `Migrations/<name>.Designer.cs` whose text has EF Core's generated shape. A file's own `<auto-generated/>` header or `linguist-generated` attribute is never trusted | no |
| `project` | `*.csproj`, `*.fsproj`, `*.vbproj`, `*.sln`, `*.slnx`, `*.slnf` | no (own signals) |
| `build-wide` | `Directory.Build.props` / `.targets` / `.rsp`, `Directory.Packages.props`, any other `*.props` or `*.targets`, `global.json`, `nuget.config`, `.editorconfig`, `*.globalconfig`, `.gitattributes` | no (own signals) |
| `test-config` | `*.runsettings`, `xunit.runner.json`, `testconfig.json` | no (own signal) |
| `test` | the nearest project is a test project — its text, or a `Directory.Build.props` above it, references `Microsoft.NET.Test.Sdk`, `xunit`, `xunit.core`, `xunit.v3`, `NUnit`, `MSTest` or `MSTest.TestFramework`, uses `MSTest.Sdk`, or sets `<IsTestProject>true` — and no production project in a directory above it would compile the file too | no |
| `production` | a `.cs`, `.fs`, `.fsi` or `.vb` file under a production project, **or a `.cs` file under no project** | yes |
| `markup` | `*.razor`, `*.cshtml` in a production project | yes |
| `docs` | `*.md` anywhere; `*.txt`, images and `docs/**` outside projects; Lockflight's own feature records under `.lockflight/features/` | no |
| `production-config` | any other file inside a production project (`appsettings*.json`, resources) | yes |
| `other` | anything else: scripts, Dockerfiles, CI files, SQL outside projects | yes |

- **A project is found from the tree, without building:** the nearest directory above the file that holds a project file.
  XML comments in a project file are ignored, so a commented-out test package changes nothing.
- **The role of a file that exists on the base branch is read on the base branch.** Adding a test package to a production
  project in the pull request does not turn its existing files into tests (the project edit has its own signal).

## What counts toward size

- **Size** is the added plus removed lines of the files whose role counts. For C#, comments and preprocessor lines are
  blanked over the whole file first, and a line that is blank or only a comment does not count. String contents are kept, so a
  line inside a multi-line string (SQL, JSON, an expected value) counts like code.
- **Reformatting does not count.** A removed and an added line of the same file that are equal once whitespace is collapsed
  are both dropped, so a reindent or a line-ending normalization is close to zero lines.
- **Binary files** count no lines; they get their own signal.

## Moves

- **An exact move** (a deleted and an added file with the same content) counts zero lines. For a source file (C#, F#, Visual
  Basic) it fires nothing else either. A moved page, setting, script or test-run setting can change what runs (page routes
  follow the path, settings are found by name and place), so it still fires the signals of a new file.
- **An edited move** (the two files' code lines at least 80 % alike, same extension) counts only the lines that differ, so a
  folder rename with a namespace change is not a large change.
- A move counts as a move **only within one role and one project**. A project that moves with its folder is still the same
  project. A file moved from a test project into production, or from one project to another, counts as an add with every
  line, so code cannot be written where it does not count and moved where it does.
- Files with identical content on more than one path are never paired, so the result never depends on file order.

## Signals

A **signal** is one fact found in the diff that raises the class to at least some value. Each has an id, the class it raises
to, a strength (`boundary` or `heuristic`) and where it was found (`path` or `path:line`). Every signal is listed, so a person
can see why a pull request is in its class. The defaults below are the `default` preset's.

### Size and shape

| Signal | Fires when | Raises to |
|---|---|---|
| `size.lines` | counted lines (production, markup, production config and other files) above `routing.fix.maxLines` (20) | `behaviour` |
| `size.files` | changed files of those roles above `routing.fix.maxFiles` (2); an exact move is not a change, an edited move is one file | `behaviour` |
| `size.large` | counted lines above `routing.largeLines` (400) | `feature` |
| `file.added` | a new production, markup, production config or other file (an exact move is not new) | `behaviour` |
| `file.deleted` | a production or markup file deleted (not moved) | `behaviour` |
| `config.changed` | a production config or other file changed | `behaviour` |
| `binary.changed` | binary content in a file of those roles | `behaviour` |
| `moved` | a move, listed for the reader | nothing |

Base exclusions (`routing.generatedPaths`, `routing.nonProduction`) keep files out of these signals only. A policy, critical or
project signal still fires for an excluded path.

### Projects and dependencies

| Signal | Fires when | Raises to |
|---|---|---|
| `deps.changed` | a package reference or version added, removed or changed (also in `Directory.Packages.props` and other props files); a line whose only change is a version value (`Version="…"`, `<Version>`, `<AssemblyVersion>`, …); a package lock file; a CI file whose only change is the ref of a `uses:` pin or the tag of an `image:` | `behaviour` |
| `project.changed` | any other project or solution file edit (`<Nullable>`, `TargetFramework`, a removed reference, a deleted project file) | `behaviour` |
| `project.policyProperty` | a project or props line touches what the build enforces, compiles or runs: `TreatWarningsAsErrors`, `WarningsAsErrors`, `CodeAnalysisTreatWarningsAsErrors`, `RunAnalyzers`, `RunAnalyzersDuringBuild`, `EnableNETAnalyzers`, `AnalysisLevel*`, `AnalysisMode*`, `EnforceCodeStyleInBuild`, `CodeAnalysisRuleSet`, `GlobalAnalyzerConfigFiles`, `EditorConfigFiles`, `IsTestProject`, an `<Import>`, `<Target>`, `<UsingTask>`, `<Exec>`, `<Analyzer>`, a `<GlobalPackageReference>`, `ExcludeAssets` / `IncludeAssets`, or a `<Compile Include/Remove>` that reaches outside the project | `routing.structural` (`critical`) |
| `project.unreadable` | a project file that cannot be read, or is not well-formed XML, on a side where it exists | `behaviour` |

A line is judged by everything on it, so a property hidden next to a package line or between comments still counts. A line
that holds nothing once its XML comments and bare `<ItemGroup>` / `<PropertyGroup>` tags (without attributes) are removed is no
change. `NoWarn` and other suppressions are the `quality.suppressions` gate step's, at every class.

### Tests

| Signal | Fires when | Raises to |
|---|---|---|
| `tests.configChanged` | a test-run setting changed (`*.runsettings`, `xunit.runner.json`, `testconfig.json`): it can filter tests or coverage | `behaviour` |
| `tests.removed` | a file of a test project deleted, or a test source file with fewer test attributes (`[Fact]`, `[Theory]`, `[Test]`, `[TestCase]`, `[TestMethod]`, `[DataTestMethod]`, `[InlineData]`, `[DataRow]`, …) at head than at base | `behaviour` |
| `tests.changed` | a code line of an existing test source file is gone at head — removed, edited, or still there inside a comment; for any other file of a test project (data, expected values, snapshots), any removed line | `behaviour` |
| `tests.skipped` | an added line of test source holds a skip marker (`Skip =`, `Explicit =`, `Skip.If` and the other `Skip.*`, `[Ignore`, `[Explicit`, `Assert.Inconclusive`, `Assert.Ignore`, `Assert.Skip*`, a `Skip` category trait) or an `#if` / `#elif` | `behaviour` |

Adding tests to a test file fires nothing: a test-only change is a `fix`.

### API surface

Declarations are compared as **sets, not diff lines**. For every changed C# file of a project, the declarations at base and at
head are read without their bodies (comments masked, string contents kept, attributes kept and sorted, both branches of an
`#if` read), keyed by the types around them, and compared per project. A reflow, a reorder, a member moved to another file of
the same project, or a `public` written in a comment or string fires nothing; an edited signature is one declaration removed
and one added. A body edit in a controller is not a feature.

| Signal | Fires when | Raises to |
|---|---|---|
| `type.added` | a production project's head declarations hold a type its base lacks | `behaviour` |
| `api.endpointAttribute` | a declaration with `[HttpGet]`, `[HttpPost]`, … `[Route]`, `[ApiController]` or `[AcceptVerbs]` added, removed or changed (a route template edit included) | `feature` |
| `api.controllerAction` | a public method of a controller or SignalR hub added, removed or changed, or the controller's own declaration (its attributes, its base) changed. A controller is named `…Controller`, marked `[ApiController]`, `[Controller]` or `[Route]`, or derives from a `…Controller` / `…ControllerBase` type | `feature` |
| `api.controllerAdded` | a new `*Controller.cs` file, or a new type deriving from a controller base, `Hub` or a gRPC `…Base` service | `feature` |
| `api.publicMember` | in an **API project**, a public or protected declaration added, removed or changed (a public constant's value included). A member of a type that is written non-public in every part is not API | `feature` |
| `api.minimalEndpoint` | a `.Map…(` registration statement (`MapGet`, `MapGroup`, `MapHealthChecks`, `Map`, …; not `MapFrom`) or an endpoint convention (`.RequireAuthorization`, `.AllowAnonymous`, …) added, removed or changed. Whole statements are compared, so a template on the next line counts, and a changed comment does not | `feature` |
| `api.pageDirective` | a Razor `@page`, `@rendermode`, `[Route(` or `@attribute [Authorize` line added or removed | `feature` |
| `api.contractFile` | a `.proto`, `openapi*.json/yaml`, `swagger*.json/yaml` or `.graphql` file changed outside test projects | `feature` |

An **API project** is a production project whose text, or a `Directory.Build.props` above it, sets `<IsPackable>true`, a
`<PackageId>` or `<GeneratePackageOnBuild>true` (a property under a `Condition` counts), or that has a `PublicAPI.Shipped.txt`,
or that matches `routing.apiProjects`, at base or at head. In an application project nearly every class is `public`, so its API
is its endpoints, not its declarations: a new public method there is not a feature by itself.

### Database

| Signal | Fires when | Raises to |
|---|---|---|
| `db.migration` | a changed path under `**/Migrations/**` (generated files included) or `routing.dbPaths` | `feature` |
| `db.sql` | a changed `*.sql` file outside test projects and `routing.nonProduction` | `feature` |
| `db.model` | an EF Core or FluentMigrator model statement added, removed or changed (`DbSet<`, `OnModelCreating`, `modelBuilder.`, `builder.Property(…)`, `builder.Has…`, `.ToTable(`, `[Migration(`, `Create.Table(`, …), or a mapping attribute (`[Table]`, `[Column]`, `[Key]`, `[MaxLength]`, `[Required]`, …) added, removed or changed on a declaration | `feature` |

An entity gaining a property is invisible to these: the `ef.pendingModelChanges` gate step is the interlock for that, where a
repository pins `dotnet-ef`.

### Policy and critical paths

| Signal | Fires when | Raises to | Strength |
|---|---|---|---|
| `critical.path` | a changed path, **either side of a move**, matches `routing.critical` read from the base branch | `critical` | boundary |
| `critical.policy` | a changed path is a policy file: the engine's [protected list](configuration.md#built-in-protected-paths) for this manifest (Lockflight's feature records under `.lockflight/features/` excepted), `CODEOWNERS`, and the files in `routing.requiredWorkflows` | `critical` | boundary |
| `ci.workflowChanged` | any other CI file changed (`.github/workflows/**`, `.gitlab-ci*.yml`, `azure-pipelines*.yml`, `bitbucket-pipelines.yml`, …), unless the edit only bumps pins | `feature` | heuristic |

- The policy list is the engine's, not the manifest's: `routing.critical` can add paths, never remove one.
- **A version-only `Directory.Packages.props` edit** (`PackageVersion` lines added, removed or re-versioned, nothing else on
  any changed line) is `deps.changed`, not `critical.policy`, so a dependency bot's pull request does not need the critical
  class. Any other edit of the file is policy, a `GlobalPackageReference` (an analyzer for every project) and an
  `ExcludeAssets` / `IncludeAssets` change included.
- **Leaving a critical path:** an exact move from a `routing.critical` path to a path outside it is a failure of the routing
  rules (`routing.criticalMove`), not only a class: add the new path to `routing.critical` on the base branch first, then move
  the file. A move with edits cannot be told apart from a delete and an add; it is `critical` through its old path.

### Structure

| Signal | Fires when | Raises to |
|---|---|---|
| `structure.projectAdded` | a new production project (a moved project is not new; a new test project fires nothing) | `routing.structural` (`critical`) |
| `structure.projectKindChanged` | a project is a test project on one side and a production project on the other (its own text or a `Directory.Build.props` above it changed) | `critical` |
| `structure.buildWide` | a build-wide file changed, other than packages and versions in a props or targets file | `routing.structural` |
| `structure.solution` | a project added to or removed from a `.sln`, `.slnx` or `.slnf`, or from the solution's build (`.Build.0` lines, `<Build>`) | `routing.structural` |
| `structure.layerViolation` | an added `<ProjectReference>` from a project in one `routing.layers` entry to a project in an outer one | `critical` |
| `structure.testReference` | an added `<ProjectReference>` from a production project to a test project | `critical` |
| `structure.referenceAdded` | any other added `<ProjectReference>` from a production project: `behaviour` when both projects are in declared `routing.layers` and it points inward, `feature` otherwise; a reference that does not resolve to a project at head (an MSBuild property other than the project's own directory, a missing file) is `routing.structural` | `behaviour`, `feature` or `routing.structural` |

`routing.structural` can be set to `feature` by a team; it can never be lower. `critical.policy` still covers the build-wide
files the protected list names (`Directory.Build.props`, `.editorconfig`, `nuget.config`, …) whatever it says.

## How the class is computed

```text
computed = max(routing.floor, every signal)
class    = max(computed, every raise)
```

There is no other precedence: signals never cancel each other and nothing subtracts. A raise (a spec's class line, a label)
comes from outside the diff and can only raise. The classification is sorted (highest class first, then id and place), so the
same change and policy always give the same list.

## What each class requires

The class decides which checks a pull request must pass. Every requirement switches on at a class and stays on above it
(`routing.require.*From`, `approvals.specFirstFrom`), and the coverage thresholds never decrease, so a higher class never needs
less. The `default` preset:

| Requirement | `fix` | `behaviour` | `feature` | `critical` |
|---|---|---|---|---|
| Gates (`pr` profile), suppressions, docs references | required | required | required | required |
| Patch coverage | 80 % with a collector | 80 % with a collector | 80 %, required (NOT-EARNED without a collector) | 90 %, required |
| EF Core pending model changes | when an EF project changed | when an EF project changed | required | required |
| Red→green | when production code changed | same | per story, same | per story, same |
| Spec and trace | trace when a spec covers it | same | spec required (`specFrom`) | spec required |
| Review (with an API key) | — | advisory (`reviewFrom`) | advisory | required; NOT-EARNED without a key (`reviewKeyFrom`) |
| Declared architecture tests | — | — | when declared (`architectureFrom`) | when declared |
| Spec first (merged before the code) | — | — | — | when `approvals.specFirstFrom` says so |

Red→green, and spec and trace, apply only when production code lines changed: a docs-only or test-only pull request needs
neither. The [configuration reference](configuration.md#lockflightyaml) lists the other presets' values.

## See the class: `route show`

`lockflight route show` prints the class of the current branch the way the pull request comment will show it:

```text
**Class: feature** · computed feature (floor fix, preset default) · db.migration `src/Infra/Migrations/20261029_AddRefunds.cs` · +1 more
Needs: gates · coverage 80 % · suppressions · docs references · ef pending changes · red→green per story · spec + trace · review (key)
```

then every signal with its place. It reads the working tree under the working tree's manifest and says so; it is advice,
and CI recomputes the class from the base branch. `--head <ref>` reads a commit pair under the base commit's policy, as CI
does, and `--json` prints the evidence block (`changeClass`: class, computed class, policy commit and manifest blob, every
signal, raises, failures, engine version; same inputs give the same bytes). See [commands](commands.md#ci).

## Guardrail or boundary

Reading the diff is deterministic, but most signals are text heuristics: **guardrails**, which a determined change can dodge.
Only `critical.path` and `critical.policy` are **boundaries**: their globs come from the base branch and both sides of every
move are in the diff, so no path in the pull request avoids them. Two limits hold even for those:

- they are boundaries **over paths, not over behaviour**: critical code can change without its path changing (below);
- they bind only where the check runs from a workflow the pull request cannot edit: a ruleset-required workflow, or an Action
  pinned by SHA in a workflow under CODEOWNERS with required review. With a plain `pull_request` trigger the platform runs the
  pull request's own copy of the workflow, which can skip routing; that pull request is `critical.policy`, but inside a
  workflow it controls. See [guardrails and boundaries](guardrails-and-boundaries.md).

## What routing does not see

- **Behaviour without a path:** a `partial class` elsewhere, a DI registration that swaps an implementation, a copy of a
  critical file with its callers redirected. Mitigation: broad critical globs that include composition roots
  (`Program.cs`, `*ServiceCollectionExtensions.cs`), and the review.
- **A change split into many small pull requests.** Each still needs its own evidence, and `size.large` catches the unsplit
  version, but a split that avoids every signal is possible.
- **Disabling a test by adding lines only**, such as an early `return;`: no code line is taken away and no marker is added.
  Mitigation: the review, and red→green on the tests the pull request needs.
- **API not written as a declaration or a mapping:** a DTO property that changes an HTTP contract in an application project,
  routes registered by libraries through their own base classes (FastEndpoints, Carter) or helper extension methods
  (`app.MapMyRoutes()`). Mitigation: `routing.apiProjects`, and the review.
- **A move with edits out of a critical path**, then edits at the new path in a later pull request: the move is `critical`
  through its old path; later edits are judged at the new path. Mitigation: broad directory globs and CODEOWNERS on them.
